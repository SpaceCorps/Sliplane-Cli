# Official Sliplane CLI (Go/cobra): service-side feature inventory vs our Rust CLI

Scope: `internal/cli/{deploy,service_create,service_create_prompt,service_deployment,service_management,service_configuration,service_environment,logs,ssh,ssh_keys,tunnel,registry,volumes,monitoring,metrics_chart,metrics_watch,infrastructure,resources}.go`, `internal/presets/catalog.go`, `internal/api/*.go` (services, service_configuration, ssh, volumes, monitoring, infrastructure, access, client, models), plus `resolve.go`, `root.go`, `output.go`, `prompt.go`, `agent_guidance.md` for cross-cutting behavior.

Official repo: github.com/sliplane/cli (clone at `scratchpad/official`, HEAD 91f49f7). README marks it "alpha". API base `https://ctrl.sliplane.io/v0`. Everything below is paraphrased from source, not quoted.

Verified facts that frame everything:
- Every Sliplane API endpoint the official service-side commands call is already in our pinned spec `spec/sliplane-openapi-0.11.0.json` (checked path by path). The live spec at ctrl.sliplane.io/spec.json is still 0.11.0 (`x-api-version`), with only a Postgres `trial`/`trialEndsAt` addition and a billing-cycle wording change (outside this area, worth a spec refresh).
- The one thing that is NOT the Sliplane API and NOT in the spec: the preset catalog, `GET https://sliplane.io/api/presets` (public JSON, no auth).
- The official CLI has no "wait until deployed" anywhere. Grepped the whole `internal/cli` tree. Every create/redeploy/pause/unpause/scale command returns on HTTP acceptance and its help text says to check `service show` and `logs`. The shipped agent guidance repeats this.
- Native Windows is not a supported release target for the official CLI (docs/releasing.md: macOS and Linux only, "Windows users can use WSL"). This matters for `ssh` and `tunnel` (see below).

## 1. Global conventions that change how every command behaves

| Thing | Official behavior | Ours |
| --- | --- | --- |
| Targeting | Services/servers/projects/SSH keys/registry creds/volumes are addressed by `<name-or-id>`. Resolution: exact ID match first, else exactly one exact (case-sensitive) name match, else error (not found, or ambiguous with the candidate IDs listed and, for services, a hint to use `--project`). | IDs only (`--project-id`, `--service-id`, ...). |
| Service lookup cost | `resolveService` lists every project and every project's services (N+1 GETs) on each invocation, then GETs the service again for commands that need full detail. | One request per command. |
| Output | Global `-o text|json` (default text, tabwriter tables). `--output json` = one JSON value, JSON Lines for `logs --follow`. Control characters in remote strings are replaced by spaces before printing (terminal-injection guard). | YAML default, `--json`. |
| Project scope | Global `-p/--project` (also from profile config) narrows service lookup; `--project=''` searches all. | n/a (explicit ids). |
| Prompts | Interactive only when stdin+stdout+stderr are TTYs and output is text (bubbletea/huh forms). Scripts/JSON never prompt; missing info is an error. Deletes need `--yes/-y` or a TTY `[y/N]`. | No prompts except key entry. |
| HTTP | 30 s timeout, no redirects followed, no retries (except one token refresh on 401 for OAuth logins), 64 KiB cap on error bodies, API key redacted from error text. | 100 s timeout, no retries. |
| Auth | `--token`, `SLIPLANE_TOKEN`, or OS keychain per profile. | `--account` required, no env key (deliberate). |

Porting note: the name-or-id idea is separable from the "implicit default" idea our AGENTS.md forbids. Resolving a name inside an explicitly chosen account is not the same hazard as a default account.

## 2. Command inventory (service-side)

Flags marked `[global]` are persistent root flags (`--profile`, `--token`, `-o/--output`, `-p/--project`, `--config`). Required positional args in `<>`. Aliases: `service`=`services`, `server`=`servers`, `project`=`projects`, `registry`=`registries`, `ssh-key`=`ssh-keys`, `env`=`envs`, `domain`=`domains`, `volume`=`volumes`, `list`=`ls`, `logs`=`log`, `metrics`=`metric`, `events`=`event`, `preset`=`presets`.

### 2.1 `sliplane preset list`  (alias `presets ls`)
- Request: `GET https://sliplane.io/api/presets` (see section 3). No API token attached, by design and by test.
- Output: rows `ID, NAME, DESCRIPTION`, JSON entries `{id, name, description, image}`, sorted by id.
- Flags: none.

### 2.2 `sliplane deploy <preset>`  (details in section 3)
- Flags: `--server <name-or-id>` (string, default empty), `--name <string>` (default: generated by preset, prompts on TTY), `--env KEY=value|KEY` (repeatable string array; forced `secret:true`; `KEY` alone reads the local environment, error if unset or empty), plus `[global] --project`.
- Requests: `GET /projects`, `GET /servers`, then `POST /projects/{projectId}/services`.
- Requires a read-write token.

### 2.3 `sliplane service create [name]`  (also reachable as `service create`)
- Flags (all strings unless noted):
  - Source: `--image` (image reference, no scheme/whitespace), `--repo` (must be exactly `https://github.com/owner/repo`, no creds/query/fragment). Exactly one is required.
  - `--server <name-or-id>`, `--registry-auth <credentialId>` (image only), `--branch`, `--auto-deploy` (bool, default true; only sent if explicitly set), `--dockerfile` (empty string = "automatic builds"; only sent if explicitly set), `--docker-context`, `--include-path` (repeatable), `--ignore-path` (repeatable).
  - Network: `--public` (bool), `--protocol` (default `http`; http|tcp|udp; error if given without `--public`), `--healthcheck` (must start with `/`; only valid with `--public --protocol http`).
  - Runtime: `--cmd`.
  - Env: `--env` (repeatable; SECRET by default; `KEY=value` or `KEY` from local env), `--public-env` (repeatable; non-secret), `--env-file` (repeatable path).
  - Volumes: `--volume NAME:/abs/path` (always creates a new volume), `--mount ID:/abs/path` (existing volume); duplicate container mount paths rejected.
- Request: `GET /projects`, `GET /servers`, `POST /projects/{id}/services` with `{name, serverId, deployment{url, registryAuthenticationId?, branch?, autoDeploy?, dockerfilePath?, dockerContext?, includePaths?, ignorePaths?}, network{public, protocol?}, env?, volumes?, healthcheck?, cmd?}`.
- Behavior beyond one request:
  - `--image` is normalized: no tag gets `:latest`; no registry host gets `docker.io/`; single-segment Docker Hub names get `library/`. So `nginx` becomes `docker.io/library/nginx:latest`.
  - Env merge order: all `--env-file` files in order, then `--env` (secret), then `--public-env`; last value per key wins.
  - Env file format: Docker-style literal lines `KEY=value` or `KEY`, blank lines and `#` lines skipped, leading whitespace trimmed, no quote stripping, no `$` interpolation, errors cite line number but not content. `KEY` alone reads the local process environment.
  - Project/server: a flag resolves by name or ID; with no flag, exactly one choice is auto-picked, several choices prompt on a TTY, otherwise it errors with "specify --project/--server".
  - TTY only: prompts for name, source type (image vs repo), and the source value.
  - Prints a receipt (id, name, status, projectId, serverId, derived `url` = `https://<managedDomain>` if public http, deployment, network); environment values are never echoed. Does not wait for readiness.

### 2.4 `sliplane service update <svc>`
- Flags: `--name`, `--healthcheck` (must start with `/`), `--cmd` (empty string removes the override), `--image`, `--repo`, `--registry-auth` (empty removes auth), `--branch`, `--auto-deploy` (bool), `--dockerfile` (empty = automatic builds), `--docker-context`, `--include-path` / `--ignore-path` (repeatable; a single empty value clears the list).
- Request: lookup, then (if any deployment flag) `GET .../services/{id}`, then `PATCH /projects/{p}/services/{s}` with only the supplied fields; `deployment` is the full current deployment object with the changed keys overlaid (so unspecified keys survive).
- Guards: an image flag on a repository service (or the reverse) is refused; "deployment type cannot be changed".
- No env flags at all on update; env changes only through `service env`.

### 2.5 `sliplane service redeploy <svc> [--tag T]`
- `POST .../services/{s}/deploy` with `{tag?}`. Ours: `services deploy`. ALREADY HAVE.

### 2.6 `sliplane service pause|unpause <svc>`
- `POST .../pause` and `.../unpause`. ALREADY HAVE.

### 2.7 `sliplane service delete <svc> [--yes/-y]`
- `DELETE .../services/{s}`. Confirms (`[y/N]`, TTY) unless `--yes`; non-TTY without `--yes` is an error. Output echoes resolved name, id, project.

### 2.8 `sliplane service list [-a]`, `service show <svc>`
- `list`: walks `GET /projects` then `GET /projects/{p}/services` per project (sequential), sorts by project, name, id; text mode also `GET /servers` to print server names; `-a` adds ids, project id, server id, created. `show`: `GET .../services/{s}`, prints source, access (private / public HTTP), URL or hostname, internal domain, custom domains with status.

### 2.9 `sliplane service env list|set|delete`
- `list <svc>`: `GET .../env`, blanks secret values, columns KEY VALUE SECRET.
- `set <svc> <key> [value]` (`--secret`, default non-secret): accepts `KEY=value`, `KEY VALUE`, or `KEY` (read local env); `PUT .../env/{key}` with `{value, secret}`.
- `delete <svc> <key>`: `DELETE .../env/{key}`.
- No import/export/bulk verb, no unset-all.

### 2.10 `sliplane service domain list|add|remove`
- `list`: `GET .../services/{s}` and read `network.customDomains` (columns DOMAIN STATUS ID). `add <svc> <domain>`: validates a bare hostname (no `/`, `:`, whitespace), `POST .../domains {domain}`. `remove <svc> <domain-or-id>`: resolves against the service's custom domains, `DELETE .../domains/{id}`.

### 2.11 `sliplane service volume list|attach|detach|update`
- `list <svc>`: `GET .../services/{s}`, reads `.volumes`. `attach <svc> <volume> <mount-path>`: volume resolved by name/ID among `GET /servers/{serverId}/volumes` (existing volumes only), `POST .../services/{s}/volumes {id, mountPath}`. `update <svc> <volume> <mount-path>`: `PATCH .../volumes/{v} {mountPath}`. `detach <svc> <volume>`: `DELETE .../volumes/{v}`. Attach/update/detach redeploy the service (API behavior). Mount path must be absolute.

### 2.12 `sliplane server volume list|create|rename`  (persistent `--server`, auto-picked if only one server)
- `GET/POST /servers/{id}/volumes`, `PATCH /servers/{id}/volumes/{vid} {name}`. ALREADY HAVE (ids only).

### 2.13 `sliplane service events <svc>`
- `GET .../events`, columns TIME TYPE TRIGGER MESSAGE. ALREADY HAVE (`services events`).

### 2.14 `sliplane logs <svc>` (also `service logs`)  (details in section 4)
- Flags: `--follow/-f` (bool), `--since <duration|RFC3339>`, `--interval <duration>` (default 2s, min 1s).
- Request: `GET .../services/{s}/logs[?from=<unix seconds>]`.

### 2.15 `sliplane metrics <name-or-id>` and `service metrics` / `server metrics`  (details in section 6)
- Flags: `--range` (default `1h`; 10min|1h|24h|7d), `--from`/`--to` (Unix seconds, both required together, mutually exclusive with `--range`), `--watch/-w`.
- Request: `GET .../services/{s}/metrics?range=...` or `GET /servers/{id}/metrics?...`.

### 2.16 `sliplane ssh <svc>`, `sliplane tunnel <svc>`  (details in section 5)
- `ssh` flags: `--ttl <duration>` (default 1h; must be >5m and <=720h), `-L/--local-forward` (repeatable `[bind:]port:host:hostport`), `-N/--no-shell`. `-N` requires at least one `-L`. Requires `--output text`.
- `tunnel` flags: `--local-port` (int, default 0), `--remote-port` (int), `--ttl`.

### 2.17 `sliplane ssh-key list [service] | register [file] | delete <key> | attach <key> <service> | detach <key> <service>`
- `list`: `GET /ssh-keys`, or `GET .../services/{s}/ssh-keys` when a service is given. `register [file]` (`--name`, default hostname; file default `~/.ssh/id_ed25519.pub`): reads a public key, rejects content containing "PRIVATE KEY", `POST /ssh-keys {name, publicKey}` (no expiry). `delete` (`--yes`): `DELETE /ssh-keys/{id}`. `attach`: `PUT .../services/{s}/ssh-keys/{keyId}`, prints host, port, username. `detach`: `DELETE` same path.

### 2.18 `sliplane registry list|show|create <name>|rename|delete`
- `GET/POST /registry-credentials`, `GET/PATCH/DELETE /registry-credentials/{id}`.
- `create` flags: `--type` (default `dockerhub`; dockerhub|ghcr|dhi|generic), `--username` (prompted on TTY if omitted), `--token-stdin`. Token sources, in order: env `SLIPLANE_REGISTRY_TOKEN`, stdin (`--token-stdin`), hidden TTY prompt. There is no `--token` flag, so the secret never lands in argv or shell history. Any occurrence of the token in an API error message is replaced with a redaction marker.

### 2.19 Server and project helpers (infrastructure.go / resources.go)
- `server create <name>` (`--instance-type` default `base`, `--location` default `ger`, `--billing-cycle` default `hourly`, `--disk-size`): `POST /servers`. Client-side checks: billing cycle in {hourly, monthly, yearly}; disk size in {50,100,250,500,1000}.
- `server scale <svr> <instance-type> [--billing-cycle]`: `POST /servers/{id}`. `server resize-disk <svr> <GB>`: pre-checks the new size exceeds the current size (extra `GET /servers`), then `POST /servers/{id}/disk`. `server delete`, `project rename`, `project delete`: with `--yes` confirmation convention.

## 3. `deploy <preset>` and the preset catalog (the deepest feature)

### 3.1 Where the catalog comes from
- `GET https://sliplane.io/api/presets` (constant in `presets.URL`; overridable in tests only). Plain unauthenticated GET, `Accept: application/json`, 30 s timeout, body capped at 4 MiB (today ~81 KB), non-200 is an error, empty `presets` is an error.
- It is NOT part of the versioned Sliplane API or its OpenAPI spec. It is the same data the dashboard uses ("the same presets as the dashboard"). Served via BunnyCDN, `Cache-Control: public, max-age=0`. No version field, so any schema drift is silent; the official client fails closed on anything unexpected.
- I fetched a copy for analysis (untrusted data): `scratchpad/research/catalog/presets.json`, 76 presets, 72 generated-value instructions.

### 3.2 Schema (observed live + parsed by official code)
Top level: `{ presets: [...], generatedValues: [...] }`.

`generatedValues[i]`: `{ placeholder: "__SLIPLANE_GENERATED_<i>__", kind: "string"|"hex"|"uuid", length: 1..128 }`.
- Placeholder must equal the index form exactly, in order, else the catalog is rejected.
- `string`: random alphanumeric, 62-char alphabet (A-Za-z0-9), `length` chars, rejection-sampled from crypto RNG.
- `hex`: `length` random BYTES, hex-encoded (so 2x chars).
- `uuid`: `length` must be 16; produces a UUIDv4 string.
- Observed kinds today: 63 string, 5 uuid, 4 hex.

`presets[]`:
- Parsed by the official client: `name`, `description`, `tags[]`, `volumes[{id, name}]`, `settings{presetId, name, deploySource, externalDockerImage, public, protocol, healthcheckPath, cmd, envs[{key,value,secret}], volumes[{id, containerMountPath}]}`.
- Present in the data but ignored by the official client: `icon`, `requirements{min,recommended}{cpu,memory(MB),disk(GB)}` (13 presets have it, e.g. n8n min 2048 MB, ollama min 8192 MB / 2 CPU), `volumes[].new` (always true), `settings.serverId` (empty).
- `settings.protocol` may be null/absent for private presets (`ollama`, `cloudflared`).
- Observed: all 76 are `deploySource: "registry"`, no duplicate `presetId`. Images come from docker.io (54), ghcr.io (13), lscr.io (3), codeberg.org (2), quay.io (2), docker.elastic.co, cr.weaviate.io.
- 74 of 76 presets are `public: true`. Seven are public non-HTTP (`postgres`, `mongo`, `redis`, `mysql`, `mariadb`, `rabbitmq`, `ssh`, all `tcp`), i.e. `deploy postgres` exposes a database on the public internet protected only by the generated password. The official CLI prints no warning.
- Two presets ship an empty required secret that the user must supply: `open-webui` and `lobe-chat` (both `OPENAI_API_KEY`).
- 9 env values contain `$SLIPLANE_DOMAIN` (e.g. n8n `N8N_WEBHOOK_URL=https://$SLIPLANE_DOMAIN`). The official CLI sends these literally and its tests assert that. The spec contains no mention of `SLIPLANE_DOMAIN`, so whether the platform expands it at runtime is UNVERIFIED (I did not create anything to find out; read-only task). Must be checked once against a throwaway service before porting `deploy`.

### 3.3 Preset to request conversion
1. `Instantiate(id)`: exact `presetId` match (duplicate = error, missing = "run preset list"). JSON-serialize that one preset, replace each placeholder that occurs with a fresh random value (same placeholder gets the same value everywhere in that one preset, so the volume id/name, service name and secret env stay consistent), error if any `__SLIPLANE_GENERATED_` text remains, re-parse. The catalog object itself is never mutated, so two deploys of the same preset get different names/secrets.
2. `presetServiceInput`:
   - Requires `deploySource == "registry"`, non-empty image and name.
   - If `public`, protocol must be http|tcp|udp.
   - Request body: `name` = `settings.name` (e.g. `n8n-ab12...`), `deployment.url` = image, `network{public, protocol}`, `cmd` = `settings.cmd`, `healthcheck` only when protocol is `http`, `env` = preset envs.
   - `--env` overrides replace a preset var by key or get appended; overrides are always `secret:true`.
   - Any env left with an empty key or value is an error telling the user to pass `--env KEY`.
   - Each `settings.volumes[]` mount is joined to `preset.volumes[]` by `id` to get the generated volume NAME, sent as `{name, mountPath}`; mount path must start with `/`. So every deploy creates NEW volumes (never reuses).
   - Ignored: tags, icon, requirements, per-preset serverId.
3. Destination: `--project` (global) and `--server` resolved by name/id; auto-pick when exactly one exists; prompt on TTY when several; error otherwise.
4. Name: `--name` overrides; otherwise on a TTY an input prompt prefilled with the generated name.
5. `POST /projects/{projectId}/services`. Prints the standard receipt (no env values). Does not wait.

### 3.4 Consequences for a port
- Generated secrets are write-only: the receipt omits env, and the API masks secret values on read (spec: "Secret values are masked"). After `deploy postgres` nobody can retrieve the generated `POSTGRES_PASSWORD` through the API. For an agent that must connect to what it just created, the port should print generated secret values exactly once (as our `buckets create-key` already does with its secret) or accept `--env POSTGRES_PASSWORD=...`. This is a design decision for you, since it differs from the official CLI.
- Trust: the catalog decides which image runs with which secrets. Same trust as the dashboard, but a CLI driven by an agent should show the image in a dry run before creating.
- Useful additions the official lacks: `presets show <id>` / `deploy --dry-run` (print the request body with secrets redacted), a `--private` switch for the 7 public TCP presets, and a memory check against `requirements.min.memory` using `GET /servers/{id}` `memoryMb`.

## 4. `logs` and `--follow`

- Endpoint: `GET /projects/{p}/services/{s}/logs`, with `?from=<unix seconds>` only when a start is known. The official CLI never sends `to`, so it never pages backwards. Response items `{createdAt (RFC3339), message}`; the API caps at 500 lines.
- `--since`: either a Go duration (`30m`, `2h`; must be positive; becomes now minus duration) or an RFC3339 timestamp.
- Every poll: results sorted ascending by `createdAt` (stable). If a response has 500 or more lines, a warning goes to stderr ("reached the 500-line limit; additional logs may be missing").
- Without `--follow`: one request. Text mode prints `<local time "YYYY-MM-DD HH:MM:SS TZ">  <message>` per line, with control characters replaced by spaces. JSON mode prints a single array.
- With `--follow` (poll loop, no websocket, no server push):
  - Sleep `--interval` (default 2 s, minimum 1 s) between polls; Ctrl-C (context cancel) ends it with a non-zero error.
  - Dedupe: a cursor tracks the latest timestamp seen and a map `(UTC timestamp, message) -> count` so genuinely repeated identical lines are still printed, while overlap is suppressed. A line is "fresh" if its count within this response exceeds the count already seen for that key.
  - Next poll's `from` = latest timestamp (whole seconds) minus 1 s. The 1 s overlap covers the API's coarse second-resolution `from`. The seen-map is pruned to keys at or after that cutoff.
  - JSON mode emits one JSON object per line (JSON Lines).
  - No error backoff: any API error aborts the follow. If more than 500 lines arrive between polls, lines are lost (documented limitation).
- Not provided: build logs ("not currently exposed"), `--tail N`, `--until`, grep, per-deployment logs.
- Ours: `services logs --from --to` is one raw call, no ordering guarantee, no 500 warning, no `--since`, no follow. PARTIAL.

## 5. `ssh` and `tunnel`: plain OpenSSH, no websocket, no proxy

The API returns an ordinary SSH endpoint; the CLI orchestrates a temporary key and then execs the system `ssh`.

Sequence (`openSSH`):
1. Require `ssh` and `ssh-keygen` on PATH (error text tells the user to install OpenSSH).
2. For `ssh -L/-N`, validate the forwarding options by running `ssh -G -F none <opts> -- localhost` (config dump only, no connection).
3. Resolve service. Create a private temp dir (`slissh-*`, removed on exit).
4. `ssh-keygen -q -t ed25519 -N "" -C sliplane-cli -f <tmp>/key`.
5. `POST /ssh-keys {name: "Sliplane CLI: <service name>", publicKey, expiresAt: now+ttl}` (ttl default 1 h, must be >5 min and <=30 days; the expiry is the fallback if the CLI dies before cleanup).
6. `PUT /projects/{p}/services/{s}/ssh-keys/{keyId}` returns `{host, port, username}`.
7. Validate that response before using it as ssh arguments: port 1-65535, username has no whitespace/NUL, host is an IP or only `[A-Za-z0-9.-]` and does not start with `-` (argument-injection guard).
8. Common ssh args: `-F none -i <key> -S <tmp>/c -o IdentitiesOnly=yes -o IdentityAgent=none -o BatchMode=yes -o StrictHostKeyChecking=accept-new -o ConnectTimeout=10 -o ConnectionAttempts=1 -o ControlPersist=30 -o ExitOnForwardFailure=yes -p <port> -l <username>`.
9. Readiness loop: start a background ControlMaster (`ssh ... -f -N -M -- host`) with output sent to a file. Because a freshly attached key takes a moment to be accepted, retry up to 12 times at 5 s spacing (1 minute overall) but ONLY while the log contains "Permission denied (publickey)"; any other failure is immediate. Message "Waiting for SSH access..." goes to stderr.
10. `tunnel` only, when the service reports no `internalPort`: probe HTTP on remote port 80 by running `ssh -S none -W localhost:80` and writing a `HEAD /` request into it (5 s timeout); failure says "specify --remote-port".
11. Run the session: `ssh <common args> [-L <fwd>]... [-N] -- host` with stdin/stdout/stderr inherited. For `-N`, `-S none` is added (a multiplexed `-N` client registers forwards and exits; a tunnel needs a foreground connection). Terminal state is saved and restored. On cancel it sends SIGINT with a 2 s grace.
12. Cleanup (runs even after Ctrl-C, on an uncancelable 30 s context): `ssh -O exit` to the control master; `DELETE .../ssh-keys/{keyId}` (detach) then `DELETE /ssh-keys/{keyId}`, treating 404 as already gone; remove temp dir.

`tunnel` specifics: picks the remote port from `--remote-port`, else the service's `network.internalPort`, else 80 (with the probe). Local port: `--local-port`, else the same number as the remote port, falling back to any free port if taken; binds `127.0.0.1` only. It checks the port is free by listening then closing, then hands `-N -L 127.0.0.1:<local>:localhost:<remote>` to the same `openSSH`. UDP services are refused. Not usable with `-o json`.

Observations that matter for porting:
- There is no remote-command form. `ssh <svc>` takes one positional; you cannot run `sliplane ssh api -- ls /app`. For an agent-driven CLI a one-shot exec is the most valuable variant, and it is the easiest thing to add on top.
- The design leans on ControlMaster/ControlPersist multiplexing. As far as I know the native Windows OpenSSH build does not support ControlMaster (not verified here; this box has Git-for-Windows `ssh` 10.3p1 in `/usr/bin`, which differs from `C:\Windows\System32\OpenSSH\ssh.exe`). A Windows-safe variant drops multiplexing: generate the key, create/attach, then retry a plain `ssh -i ... -p ... user@host [-L ...]` on "Permission denied (publickey)" up to the same budget.
- Cleanup-on-interrupt needs the parent to survive Ctrl-C while ssh is in the foreground. Rust's default SIGINT/Ctrl-C terminates the parent immediately, which would leak the temporary key until its `expiresAt`. That is exactly the case the TTL fallback exists for, so it is tolerable, but a clean port wants a small Ctrl-C handler (`ctrlc` crate or `windows-sys` `SetConsoleCtrlHandler` / `libc`).

## 6. Metrics: `metrics`, `metrics --watch`

- Request: `GET .../metrics?range=<r>` or `?from=<s>&to=<s>` for a service, or the same under `/servers/{id}/metrics`. Items `{createdAt, cpuUsage (%), usedMemory, freeMemory, totalMemory}` (memory in bytes; the chart divides used memory by 1 MiB).
- Validation client-side: range must be 10min|1h|24h|7d; `--from/--to` must be positive, increasing, and not combined with `--range`.
- Top-level `metrics <name>` with no kind resolves the name as a service and as a server; exactly one must match, both matching is an error telling you to use `service metrics` or `server metrics`.
- Text mode: two braille line charts (CPU %, Memory MiB) drawn with bubbletea + lipgloss + ntcharts; titles show latest and peak; X axis in local time (date format when the span is 24 h or more); Y axis from 0 to peak with 10 percent headroom; width capped at 120; says "no metrics available" when empty. JSON mode: the raw array.
- `--watch/-w`: bubbletea full-screen program; refetch every 5 s, scheduled after the previous response (no overlapping requests); `q` or Ctrl-C quits; needs an interactive TTY with text output; incompatible with `--from/--to`.
- None of this is useful to an LLM agent; the raw series is already what we print. The only reusable idea is the summary line (latest and peak), which is a few lines of arithmetic.

## 8. Value ranking for an LLM-agent-driven CLI (MISSING / PARTIAL only)

1. `deploy <preset>` + `presets list/show` (+ `--dry-run`, `--private`, one-time display of generated secrets). High value, EASY to MEDIUM. Needs RNG, one unauthenticated GET, and the `$SLIPLANE_DOMAIN` question answered.
2. Log reading ergonomics: `--since` (duration/RFC3339), ascending sort, 500-line warning, bounded `--follow` with JSON Lines. High value, EASY.
3. Wait-for-live (`services wait`, or `--wait` on create/deploy). Not in the official CLI at all, so do not look there for a design; high value, EASY, endpoints in spec.
4. `ssh` / `tunnel` using system OpenSSH, ideally plus a one-shot remote command form. Medium-high value, MEDIUM (HARD on native Windows only if multiplexing is copied; use the plain-ssh retry variant).
5. `--env-file` and local-environment pass-through for env values, plus taking the registry credential token via stdin/env instead of `--token`. Medium value, EASY, a real secret-hygiene gain.
6. Name-or-ID resolution. Medium value, EASY, optional because it adds requests and risks wrong-target mistakes if ambiguity handling is loose; copy the official rule (exact ID, else a unique exact name, else error listing IDs).
7. `--image` normalization/validation and clear-on-empty update semantics. Medium-low, EASY; verify the empty-value semantics live first.
8. Small defaults and read-only helpers (`ssh-key register` defaults, `domain list`, `volume list`). Low value, EASY.
9. Delete confirmations, metric charts and watch, server-create defaults. Skip (or only echo the resolved name on delete).

Open verification items before coding (none were tested; this task was read-only):

- Does `dockerfilePath: ""` mean automatic builds, and `cmd: ""` remove the override? (official claims; not in spec 0.11.0)
- Does native-Windows OpenSSH support ControlMaster? (believed no)
- Preset catalog stability: unversioned, unofficial endpoint.
